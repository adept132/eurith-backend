# Развёртывание Eurith API

Сервер разворачивает только уже проверенный commit или tag из GitHub. Рабочие
файлы на сервере вручную не редактируются.

После одноразовой настройки обновление выполняется из `/opt/eurith`. Скрипт
намеренно не имеет версии по умолчанию: нужно передать проверенный commit или tag:

```bash
./backend/deploy/deploy.sh 0123456789abcdef
# или
./backend/deploy/deploy.sh v1.2.0
```

Скрипт останавливается при незакоммиченных серверных изменениях, делает дамп
PostgreSQL и закрытого тома фото, собирает новый образ, применяет Alembic-миграции, проверяет публичный
`/health` и возвращает предыдущий commit, если проверка не прошла.

## Новое изменение схемы БД

Модель SQLAlchemy и миграция меняются в одном commit. Локально, с запущенной
тестовой PostgreSQL:

```bash
alembic revision --autogenerate -m "add example field"
alembic upgrade head
```

Автоматически созданную миграцию нужно прочитать и проверить до commit. Миграции
production выполняет `deploy.sh` после резервной копии и до перезапуска API.

Пароли, `.env` и Firebase service account не хранятся в GitHub.

## P1-07: приватные фото прогресса

Перед выпуском создайте на сервере **постоянный** каталог `/opt/eurith/private/body-photos`.
Его владелец — UID/GID `1000:1000` (пользователь API в Dockerfile), права каталога
`0700`. Каталог должен оставаться за пределами репозитория, образа и публичного
`/media`; HTTP-сервер не должен раздавать его напрямую. Внешний compose-файл в
`/opt/eurith` должен содержать для сервиса `api`:

```yaml
environment:
  BODY_PHOTO_ROOT: /var/lib/eurith/body-photos
volumes:
  - /opt/eurith/private/body-photos:/var/lib/eurith/body-photos:rw
```

Подготовка каталога на новом сервере:

```bash
sudo install -d -m 0700 -o 1000 -g 1000 /opt/eurith/private/body-photos
```

`deploy.sh` проверяет наличие каталога и перед переключением версии кладёт в
`/opt/eurith/backups` два файла с одним префиксом: дамп PostgreSQL `.dump` и
архив фото `-body-photos.tar`. Скрипт устанавливает `umask 077`. Эти файлы нужно
переносить в закрытое резервное хранилище и хранить **как пару**. При большом
объёме фото учтите время и место для полного снимка перед каждым релизом.

Проверка восстановления на отдельном тестовом сервере: восстановить дамп через
`pg_restore`, распаковать соответствующий архив в пустой приватный каталог,
назначить владельца `1000:1000` и права `0700`, затем проверить авторизованное
открытие фото, отсутствие доступа через `/media`, удаление и вход со второго
устройства. Восстанавливать только доверенный архив и вне работающего production
API. После восстановления сверить количество активных строк
`body_progress_photos` и файлов полного размера/миниатюр.

Если том или `BODY_PHOTO_ROOT` недоступны, только маршруты фото возвращают 503;
остальная часть API продолжает работать. Перед production-выпуском нужны TLS для
API, проверка прав каталога и тест восстановления пары БД + фото.
Отложенная очистка после ошибки диска повторяется при старте API и ежедневным
запуском `python -m scripts.purge_deleted_accounts --apply`.
